# 설계 결정 기록

코드와 명세가 "왜 이렇게 했는지"를 적는다. 번호(D1, D2 …)는 다시 쓰지 않고, 결정을 뒤집으면 새 번호로 적고 옛 결정에 "→ Dn으로 대체"를 단다.
코드 주석·명세·커밋에서 `D7`처럼 번호로 가리킨다.

형식: 결정 / 이유 / 버린 대안 / 관련 명세.

---

## D1. API는 oRPC 계약 우선(contract-first)으로 정의한다 (2026-11-05)

- **결정**: `packages/contracts`에 모든 절차의 입력·출력 Zod 스키마와 타입 있는 오류(`EMAIL_TAKEN`, `ACCOUNT_LOCKED { retryAfterSeconds }` …)를 둔다. 서버는 `implement(contract)`로 구현하고 클라이언트는 같은 계약에서 타입과 폼 검증 스키마를 얻는다.
- **이유**: 서버 코드를 import하지 않고도 웹·데스크톱·모바일이 같은 타입을 쓴다. 오류도 계약의 일부라서 클라이언트가 `error.code`로 분기할 수 있고, 폼 검증과 서버 검증이 어긋나지 않는다.
- **버린 대안**: tRPC(서버 라우터 타입에 클라이언트가 묶인다), OpenAPI 코드 생성(생성 단계가 늘고 생성물이 스펙과 어긋나기 쉽다).

## D2. 리프레시 토큰은 매번 회전하고, 재사용되면 패밀리 전체를 폐기한다 (2026-11-05)

- **결정**: 리프레시할 때마다 새 토큰을 발급하고 옛 토큰을 폐기한다. 이미 쓴 토큰이 다시 오면 같은 패밀리의 모든 토큰을 폐기한다. DB에는 SHA-256 해시만 저장한다. 폐기는 `UPDATE ... WHERE revoked_at IS NULL`로 해서 동시에 들어온 두 요청 중 하나만 이긴다.
- **이유**: 리프레시 토큰이 유출돼도 정상 사용자와 공격자 중 한쪽이 옛 토큰을 쓰는 순간 탐지된다. DB가 유출돼도 해시만으로는 세션을 이어 갈 수 없다.
- **버린 대안**: 회전 없는 장수명 리프레시 토큰(유출을 알 방법이 없다), 서버 세션 저장소(클라이언트 종류마다 다른 저장 방식이 필요하다).
- **관련 명세**: AUTH-8~11

## D3. 웹의 리프레시 토큰은 HttpOnly 쿠키에 두고, CSRF는 커스텀 헤더로 막는다 (2026-11-05)

- **결정**: 웹은 리프레시 토큰을 `HttpOnly; SameSite=Strict; Path=/rpc/auth` 쿠키로 받는다. 서버는 `x-client-kind: web` 헤더가 있을 때만 쿠키를 읽고 쓴다. 액세스 토큰은 메모리에만 둔다.
- **이유**: 페이지 스크립트가 쿠키를 읽을 수 없으니 XSS로 리프레시 토큰을 훔칠 수 없다. 다른 사이트의 폼이나 단순 요청은 커스텀 헤더를 붙일 수 없으므로 별도 CSRF 토큰 없이 CSRF를 막는다.
- **버린 대안**: localStorage(XSS 한 번에 장기 세션이 털린다), 동기화 CSRF 토큰(상태 관리가 늘어난다).
- **관련 명세**: AUTH-15

## D4. 액세스 토큰의 audience는 클라이언트 종류다 (2026-11-05)

- **결정**: 액세스 토큰은 15분짜리 HS256 JWT이고 `aud`가 `web` 또는 `native`다. 서버는 요청의 클라이언트 종류와 같은 audience만 받는다.
- **이유**: 한 클라이언트 종류에 발급된 토큰은 그 종류의 보호 규칙(웹은 쿠키·헤더 규칙) 안에서만 쓰이게 한다. 웹에서 빼낸 액세스 토큰을 네이티브 클라이언트로 재생(replay)하면 거부된다.
- **관련 명세**: AUTH-13

## D5. 클라이언트는 리프레시를 하나만 띄우고 호출자들이 함께 기다린다 (2026-11-05)

- **결정**: `packages/api-client`가 진행 중인 리프레시 하나를 공유한다(single-flight). 만료된 토큰으로 동시에 실패한 호출들은 그 리프레시를 기다렸다가 한 번씩 다시 보낸다.
- **이유**: D2 때문에 같은 리프레시 토큰으로 두 번 리프레시하면 재사용으로 보고 세션이 끊긴다. 클라이언트 쪽에서 동시성을 막아야 한다. 데스크톱은 같은 이유로 앱 인스턴스를 하나만 띄운다.
- **관련 명세**: AUTH-16, AUTH-17

## D6. 데스크톱은 메인 프로세스가 세션과 네트워크를 갖고, 렌더러는 브리지로만 부른다 (2026-11-05)

- **결정**: 렌더러는 샌드박스·컨텍스트 격리 상태이고 CSP가 `connect-src 'none'`이다. API 호출은 `window.desktop.rpc`로 메인에 부탁하고, 메인이 허용 목록·계약 검증을 거쳐 보낸다. 리프레시 토큰은 `safeStorage`로 암호화해 메인만 읽는다.
- **이유**: 렌더러가 XSS로 뚫려도 토큰을 읽거나, 세션 절차를 부르거나, 다른 서버로 데이터를 보낼 수 없다.
- **버린 대안**: 렌더러에서 웹 앱과 같은 방식으로 직접 호출(쿠키·토큰이 렌더러에 노출된다).
- **관련 명세**: DESK-1~15

## D7. 인가는 읽고 쓰는 SQL 문 안에서 하고, 볼 수 없는 리소스는 NOT_FOUND로 답한다 (2026-11-05)

- **결정**: 워크스페이스 멤버 여부를 `INSERT ... SELECT`, `UPDATE/DELETE ... WHERE EXISTS`처럼 같은 문에 넣는다(`apps/server/src/features/workspaces/access.ts`). 멤버가 아니면 `FORBIDDEN`이 아니라 `NOT_FOUND`다.
- **이유**: 확인과 실행 사이에 멤버가 내보내지는 경쟁 조건(check-then-act)이 없다. 멤버를 내보내는 순간 접근이 끝난다. `FORBIDDEN`은 리소스가 있다는 사실을 알려 준다.
- **관련 명세**: WS-2, WS-7, WS-11

## D8. 목록은 `(created_at, id)` 키셋 페이지네이션이고, 시각은 밀리초 정밀도로 저장한다 (2026-11-05)

- **결정**: 커서는 마지막 항목의 `(created_at, id)`를 인코딩한 불투명 문자열이다. 타임스탬프는 밀리초 정밀도로 저장한다.
- **이유**: 오프셋 페이지네이션은 새 글이 들어오면 항목이 밀려 중복·누락이 생긴다. PostgreSQL 기본 마이크로초를 JavaScript `Date`(밀리초)로 오가면 커서가 정확히 돌아오지 않는다.
- **관련 명세**: COM-1, COM-2, NOTI-4

## D9. 실시간 알림은 PostgreSQL LISTEN/NOTIFY와 SSE로 보낸다 (2026-11-05)

- **결정**: 알림 행을 댓글·좋아요와 같은 트랜잭션에서 쓰고 그 안에서 `pg_notify`를 부른다. 서버 인스턴스마다 `LISTEN` 연결 하나를 두고 자기 인스턴스의 SSE 스트림으로 나눠 준다.
- **이유**: PostgreSQL은 커밋된 뒤에만 NOTIFY를 전달하므로 롤백된 알림이 나가지 않는다. 이미 있는 DB만으로 여러 인스턴스에 팬아웃할 수 있다. 알림은 서버 → 클라이언트 단방향이라 SSE로 충분하고 oRPC 이벤트 이터레이터로 타입을 유지한다.
- **버린 대안**: Redis pub/sub(인프라가 하나 늘어난다), WebSocket(양방향이 필요 없고 인증·재연결을 따로 만들어야 한다), 프로세스 메모리 팬아웃(인스턴스가 둘 이상이면 깨진다).
- **관련 명세**: NOTI-6~8

## D10. 서버는 빌드 단계 없이 Node 타입 스트리핑으로 실행한다 (2026-11-05)

- **결정**: `node src/main.ts`로 TypeScript를 바로 실행한다(Node 22.18+). 공통 tsconfig가 `erasableSyntaxOnly`·`verbatimModuleSyntax`·`allowImportingTsExtensions`를 켠다.
- **이유**: 번들러·트랜스파일러 설정과 소스맵 문제가 없고, 테스트·개발·운영이 같은 파일을 실행한다.
- **대가**: `enum`·`namespace`·생성자 매개변수 프로퍼티를 쓸 수 없고 import에 `.ts` 확장자가 필요하다.

## D11. AI 에이전트 작업은 명세·가드로 기계적으로 묶는다 (2026-11-05, 2026-11-25 보강)

- **결정**: 동작은 `docs/specs`의 시나리오 ID로 정의하고, 테스트 제목이 그 ID로 시작한다. `spec-check`(명세 형식·시나리오↔테스트·코드 경로), `edit-guard`(명세 먼저·테스트 먼저), `commit-guard`(타입 탈출구·비밀값·메시지 형식)가 사람 리뷰 전에 규칙을 강제한다.
- **이유**: 에이전트는 지시를 잊거나 "일단 돌아가게" 고치기 쉽다. 규칙을 문서로만 두지 않고 실패하는 검사로 만들면, 에이전트가 막힌 메시지를 보고 스스로 올바른 순서(명세 → 테스트 → 코드)로 돌아온다.
- **2026-11-25 보강**: 모든 소스 파일이 승인·완료 명세의 코드 경로에 속해야 한다는 검사를 더했다. 명세 없이 새 기능 파일을 만들 수 없다.

## D12. 에이전트 규칙의 정본은 AGENTS.md이고, CLAUDE.md는 이를 불러온다 (2026-11-25)

- **결정**: 공통 규칙은 루트 `AGENTS.md`, Claude Code 전용(스킬·훅·권한)은 `CLAUDE.md`(`@AGENTS.md` import), 앱별 세부 규칙은 `.claude/rules/*.md`(경로가 맞을 때만 로드), 반복 절차는 `.claude/skills/*/SKILL.md`에 둔다. Turborepo가 AGENTS.md를 자동 생성하지 않게 `turbo.json`의 `agentGuidance`를 끈다.
- **이유**: 여러 에이전트 도구가 같은 규칙을 읽게 하면서, 루트 파일은 짧게 유지하고 앱별 맥락은 필요할 때만 읽혀 컨텍스트를 아낀다.

## D13. 모바일은 아직 실시간 알림 스트림을 열지 않는다 (2026-11-05)

- **결정**: 모바일의 알림함과 배지는 화면에 포커스가 올 때 다시 읽는다.
- **이유**: 백그라운드에서는 OS가 연결을 끊으므로 푸시 알림이 필요하고, 포그라운드 스트림만으로는 경험이 반쪽이다. 푸시 인프라가 필요해 이 저장소의 범위 밖으로 둔다.

## D14. 요청 횟수 제한은 PostgreSQL의 고정 창 카운터로 한다 (2026-11-25)

- **결정**: 가입·로그인·리프레시를 `<절차>:<IP>` 키의 고정 창(fixed window)으로 센다. 카운터는 `rate_limit_buckets` 행 하나이고, `INSERT ... ON CONFLICT DO UPDATE` 한 문으로 증가·창 재시작·판정 값을 함께 얻는다. 클라이언트 IP는 연결 주소이고, `TRUST_PROXY`를 켰을 때만 `X-Forwarded-For`의 첫 주소를 쓴다.
- **이유**: 서버가 여러 대여도 합쳐서 세야 하고(D9와 같은 이유로 인프라를 늘리지 않는다), 동시 요청이 한도를 넘지 못하게 행 잠금 하나로 직렬화한다. 고정 창은 경계에서 최대 두 배까지 몰릴 수 있지만, 인증 절차의 대입 공격을 막는 데는 충분하고 키마다 행 하나라 저장이 늘지 않는다.
- **버린 대안**: 인스턴스 메모리(서버 N대면 한도가 N배), Redis(인프라 추가), 슬라이딩 윈도·토큰 버킷(요청마다 기록이 늘거나 계산이 복잡해진다).
- **관련 명세**: RATE-1~10
